# Common Note Rules

このファイルは`.codex/skills`配下のすべてのノート作成・レビューSkillが読む共通ルールです。

## 最優先事項

最優先するのはTemplateへの準拠でも専門用語の多さでもなく、**読者が対象を正確かつ無理なく理解できる説明を作ること**です。

構造、見出し、図、Table、具体例は説明を助けるための手段です。
SkillのCheck項目を埋めること自体を目的にしません。
普通に「この技術について詳しく説明して」と質問された時に自然に行う説明より、Skill適用後の方が薄く、硬く、読みにくくなってはいけません。

## Research Directory名は「〜リサーチ」を基準にする

Documentation、Specification、Repository、Blog、Sampleなど複数の一次Sourceを調査して再構成するDirectoryは、調査成果をまとめた集合だと分かるように命名します。

ルートDirectoryは原則として`<技術名>リサーチ`を使います。
子Directoryも、何を調査した集合かが分かる`<技術名またはテーマ>リサーチ`を基本にします。

良い例:

```text
AP2リサーチ
AP2 v0.2仕様リサーチ
AP2プロトコル連携リサーチ
AP2 SDK・実装リサーチ
AP2の進化・標準化リサーチ
x402リサーチ
x402 v2仕様リサーチ
```

避ける例:

```text
AP2ドキュメントリサーチノート
AP2 v0.2仕様リサーチノート
AP2 公式・関連情報 日本語ノート
プロトコル連携
SDKとリファレンス実装
Evolution & Standardization
```

**`リサーチ`を機械的に付けるのはResearch Directoryだけです。各NoteのTitleへ`リサーチ`や`リサーチノート`をSuffixとして付けません。**
Noteは通常の記事名として、何を学ぶかが自然に分かるTitleにします。

固有のSpecification Family名を残す場合は`AP2 Community Specification 2025.0リサーチ`のようにします。

`Directory Research Naming Missing = 0`、`Research Suffix On Note = 0`を完成条件とします。

## 既存Standalone Noteを勝手にResearchへ吸収しない

Research Directoryを追加するだけの作業で、既存のOverview / Mechanism / Implementation Noteを自動的にDirectory配下へ移動・改名・削除してはいけません。

既存Noteは原則として同じ`id`、`permalink`、カテゴリ上の配置を維持します。
Research側に横断調査の入口が必要なら、既存Overviewを使い回さず別ID・別PermalinkのResearch用Noteを作ります。

既存Noteの統合・移動・削除は、ユーザーが明示的に承認した場合だけ行います。

## 読者

指定がなければ、そのテーマを初めて学ぶ技術者を想定します。
一般的なWeb、Application、Account、HTTP程度以外の専門知識は、必要に応じてその場で説明します。
知らない用語を別の知らない用語だけで説明しません。

## 記事は会話から独立して読める形にする

ノートはチャットやレビュー会話の続きではありません。
読者は、執筆前のやり取り、修正理由、以前の誤解、ユーザーからの指摘、前Versionで何が不足していたかを知りません。
**記事だけを初めて開いた人が、その記事の中だけで自然に理解を始められる状態を必須とします。**

会話で出た前提や訂正理由を、そのまま本文の前提へ持ち込みません。
例えば次のような書き方は、記事内で先にその対比や誤解を説明していない限り避けます。

- `〜というわけではありません。`
- `〜ではない点に注意してください。`
- `先ほど説明したように〜。`
- `前の説明では〜。`
- `誤解されがちですが〜。`
- `ここで重要なのは、実は〜。`

否定や対比そのものを禁止するわけではありません。
必要な場合は、**記事内で何と何を比較しているのか、なぜその区別が必要なのかを先に作ってから**使います。
読者が知らない会話上の誤解を訂正する文からSectionを始めません。

また、未導入の固有名詞や略語をSection冒頭へいきなり置き、`XはYです`の一文だけで説明を開始しません。
まず、その語が必要になる場面、解こうとしている問題、Flow上の役割などを短く示し、読者が「なぜ今この語が出るのか」を理解できる状態を作ってから名前と定義を置きます。

必要な技術的前提は記事内で作ります。
不要なのは**チャットで共有された前提**であり、初学者が理解するための文脈まで削ってはいけません。

`Conversation Context Leakage = 0`、`Unintroduced Corrective Opening = 0`、`Bare Definition Opening = 0`を完成条件とします。

## 用語導入契約

**用語を出しただけでは説明したことになりません。**

重要なConcept、Evidence、Role、Field、Mechanism、Security Controlを本文へ初めて出した時、その用語には説明責任が発生します。
必要な範囲で、近接する本文または明確に接続された後続Sectionに次を持たせます。

1. 何なのか。
2. なぜここで必要なのか。
3. 何を観測・表現・制御するものか。
4. そこから何が分かるのか。
5. それだけでは何は分からないのか。
6. 前後のConceptとどう違い、どうつながるのか。
7. Flow上のどの判断・処理で使うのか。
8. 無い、失敗する、値が違う場合に何が変わるのか。

すべての用語に8項目を機械的に書く必要はありません。
しかし、読者がその用語を見た後に「それで何が分かるの？」「それは何に使うの？」と当然疑問に思う状態のまま放置してはいけません。

### 未解決用語を残さない

執筆時は内部作業として**Term / Concept Ledger**を持ちます。
最低限次を追跡します。

| 項目 | 内容 |
|---|---|
| Term | 本文へ導入した重要語 |
| First Appearance | 初登場Section |
| Reader Question | その語を見た読者が持つ自然な疑問 |
| Explained At | 意味・役割・限界を説明したSection |
| Used At | 後続Flow / Decisionで実際に使うSection |
| Status | Resolved / Partial / Unresolved |

Critical / Majorな用語に`Partial / Unresolved`が残る状態で完成扱いにしません。

「後で説明する」構造は許可しますが、初登場時に読者が最低限迷わない一文を置き、後続Sectionへ自然に接続します。

## List / Tableは説明の代替ではない

ListやTableは情報を整理するために使います。
名称や例を並べるだけで説明を終えてはいけません。

次は説明不足です。

- 用語を5個並べて「このようなものがあります」で終わる。
- `Evidence | 用途`だけの表を置き、各Evidenceから何が分かるかを書かない。
- Tableの内容を本文で言い換えるだけで、因果関係や結論を説明しない。
- 読者が各用語を外部検索しないとSectionの意味を理解できない。

重要な一覧では、必要に応じて`何を確認する / 分かること / 分からないこと / 後続判断`まで分けます。
そしてTableの後に、**この一覧から何を理解すべきか**を文章で説明します。

## 日本語を説明の主言語にする

日本語ノートでは意味の説明を日本語で行い、英語は必要な識別子として使います。
英語の専門語を多く並べることを精密さ、専門性、技術力の表現とみなしません。

次は必要に応じてそのまま使えます。

- 仕様上の正式名称、Protocol名、Role名。
- API名、HTTP Header、Field名、Claim名、Schema名。
- Code、Command、Config、Identifier。
- 原文との照合や検索に必要な語。
- 日本語へ訳すと意味が不正確になる固有概念。

それ以外の一般的な技術概念は原則日本語で書きます。
正式語を残す場合は、最初に日本語で意味を説明し、必要なら括弧で英語を添えます。

## 専門用語を使う基準

専門用語は「知っている人には短く書ける」ためではなく、意味を一意にする必要がある時に使います。

一度意味を確立した後は短く使って構いません。
ただしCryptographic Verification、Authentication、Authorization、Trust、Settlement、Business Outcomeなど、意味が異なる概念を混同しません。

本文では必要に応じて「暗号学的な検証」、「本人確認」、「権限判断」、「信頼判断」、「資金決済」、「業務上の成功」のように意味が分かる日本語を優先します。

## 説明の深さ

内容の重要度に応じて説明量を変えます。
中心概念は十分に深く説明し、補助概念は必要な範囲に留めます。
複数の概念を同じ長さのSectionへ機械的に揃えません。

中心概念について必要に応じて次をつなげます。

- 何なのか。
- なぜ必要なのか。
- 何が問題だったのか。
- どう動くのか。
- なぜその仕組みで目的を達成できるのか。
- 前後の要素とどうつながるのか。
- 具体例では何が起きるのか。
- 何を保証し、何を保証しないのか。

重要な概念を定義1〜2文と簡単な例だけで終わらせてはいけません。

## 自然な構造を優先する

固定の章構成は持ちません。
読者が次に疑問に思うことへ答える順序を優先します。
関連する概念は同じSectionで一緒に説明して構いません。
説明を分割した結果、各Sectionが薄くなるなら統合します。
見出し数を増やすことを品質向上とみなしません。

## 見出し

見出しは目次として読める、短く意味の通るTopic名にします。
可能なら日本語だけで意味が分かる見出しを優先します。
見出しへ本文の結論を丸ごと押し込みません。

英語の公式見出しを直訳しただけの表現や、固有名詞へ`の仕組み`を付けただけの曖昧な表現は避けます。
見出しだけを読んでも、そのSectionで何を説明するかが日本語で分かるようにします。

ただし説明文をそのまま見出しにして長文化しません。
短く自然で、意味のある日本語を優先します。

## 段落と改行

1文1段落を強制しません。
日本語本文は原則として、文末の`。`ごとにMarkdown Source上で改行します。
同じ論点に属する文は行を分けても間に空行を入れず、1つのParagraphとして扱います。
Paragraphを分ける場合だけ空行を入れます。

List、Table、Blockquote、Code Block、Mermaid、Front Matterは構文上必要な形を優先します。

## 日本語の句読点と鉤括弧

独立した語句を鉤括弧で並列する場合は`「A」、「B」、「C」`のように読点で区切ります。
長い列挙は文章へ詰め込まずListへ分けます。

## 具体例

具体例はCheck用ではなく説明を前へ進めるために使います。
数字や条件を出した場合、その後のFlowや判断で実際に使います。
同じ例を繰り返すだけではなく、例を進めながら概念の違いや因果関係を見せます。

## 事実確認

Version、標準Status、Field、Header、必須・Optional、Security Requirementなど変更され得る事実は一次情報で確認します。
DraftとStableを混同しません。
推測を仕様上の事実として書きません。

## Source

ノートは`contents/<domain>/<collection>/<note>.md`で管理します。
既存ノートは原則として同じURL・同じIDを維持して更新します。
読者に意味のある既存ノート更新では`_data/article_changes.yml`も更新します。

## 更新日時

ノートを新規作成または本文・Fact・構造を更新した場合、Front Matterへ`reviewed_at`を日本時間`YYYY-MM-DD HH:MM JST`でQuoteして記録します。
旧`reviewed`は互換表示用のLegacy Fieldとして扱い、新規更新では`reviewed_at`を正とします。

`_data/article_changes.yml`の新しい意味のある更新履歴も同じ精度の日本時間を記録します。
過去Entryに正確な時刻が存在しない場合は推測して補完しません。

## Public safety

公開してよい情報だけを書きます。
会話Context、実案件、顧客、社内Project、未公開Architecture、Secret、Token、個人情報などをノートへ持ち込みません。

## 完成条件

完成したSectionについて、読者が自分の言葉で次を説明できるか確認します。

- 何を説明するSectionだったか。
- 重要な用語が何を意味するか。
- その用語から何が分かり、何は分からないか。
- 前後の処理や判断へどう接続するか。

さらにTerm / Concept LedgerのCritical / Majorに`Partial / Unresolved`が0であることを確認します。
`Directory Research Naming Missing = 0`、`Research Suffix On Note = 0`、`Existing Standalone Note Absorbed Without Approval = 0`、`Literal Translation Heading = 0`、`Meaningless English Heading = 0`、`Conversation Context Leakage = 0`、`Unintroduced Corrective Opening = 0`、`Bare Definition Opening = 0`であることも確認します。
答えがNoなら、Sectionを深める、用語を説明する、順序を変える、別Sectionと統合するなどして修正します。
