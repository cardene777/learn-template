# Overview Note

現在のチャットで話し合った内容を、後から短時間で全体像を思い出せる概要ノートへ整理し、対象Learn repositoryへ保存します。

ユーザーに`contents/`の配置、frontmatter、ファイル名、検証方法、Commit方法を指定させないでください。repositoryを読んでSkill側で判断します。

## Sourceの優先順位

ノートのSourceは次の順で扱います。

1. 現在のチャットでユーザーと話し合った内容。
2. ユーザーがチャットへ提示したURL、ファイル、コード、資料。
3. 対象repository内の既存ノートと構成情報。

ユーザーが追加調査を依頼していない場合、会話に無い論点を大量に追加して別の解説記事へ変えないでください。

会話内の情報だけでは断定できない内容は補完せず、必要なら「未確認事項」として明示します。

## Overview Noteの責務

概要ノートでは主に次を整理します。

- テーマが何か。
- 何のために使うか、なぜ重要か。
- 会話で登場した主要な概念や用語。
- 全体を理解するための関係性。
- 会話で得られた重要な結論や注意点。

内部実装の詳細、逐次的な処理フロー、コンポーネント単位の挙動が中心になる場合は`mechanism-note`の責務です。

両方のSkillが使われる場合、概要ノートへ仕組みの詳細を重複して書かず、全体像を理解するために必要な範囲だけ残します。

## 実行フロー

### 1. 対象repositoryを確定する

ユーザーが指定したGitHub repositoryを対象にします。

既に会話内でrepositoryが確定している場合は再質問しません。

### 2. repositoryのノート構成を確認する

最低限次を確認します。

- `contents/`配下のdirectory構成。
- 同じテーマまたは近いテーマの既存Markdown。
- 近隣ノートのfrontmatter。
- ファイル名、`id`、`permalink`、`order`、カテゴリ、コレクションの命名規則。

frontmatterの項目を記憶だけで固定しないでください。現在のrepositoryにある近隣ノートをSource of Truthとして扱います。

### 3. 配置先を決める

既存カテゴリとコレクションで自然に分類できる場合はそこへ追加します。

適切な分類が無い場合だけ、新しいカテゴリまたはコレクションを作ります。その場合も既存のslugと表示名の規則に合わせます。

同一テーマの概要ノートが既にある場合は、重複ファイルを増やす前に既存ノートの更新を優先します。ただし既存本文を不用意に削除せず、会話内容を自然に統合します。

### 4. 会話内容から概要を抽出する

ユーザーがテーマを指定した場合は、そのテーマに関係する会話だけを抽出します。

「この会話で話した内容」のようにテーマ指定が無い場合は、会話の中心テーマを特定してまとめます。

一時的な操作ログ、Tool実行の細部、README修正など、学習ノートとして価値が低いメタ会話はテーマ理解に必要な場合を除いて含めません。

### 5. Markdownを書く

近隣ノートのfrontmatter形式を踏襲します。

本文はテーマに応じて調整しますが、基本的には次の情報が短時間で分かる構成にします。

```markdown
## 概要

## 何のためのものか

## 主要な概念

## 全体像

## 重要なポイント

## 未確認事項
```

情報が無い見出しを機械的に残さないでください。

Mermaidや表が全体像の理解に有効な場合は使って構いません。ただし概要ノートを巨大な詳細設計書にしません。

### 6. 検証する

保存前に次を確認します。

1. frontmatterが近隣ノートのschemaと一致している。
2. `id`と`permalink`が既存ノートと衝突していない。
3. 配置先のカテゴリとコレクションが妥当である。
4. 会話で話していない内容を事実として過剰に追加していない。
5. 同一テーマの既存概要ノートを不用意に重複作成していない。
6. repositoryの実行環境を使える場合は`npm run check`を実行する。

CLIを実行できない環境では、実行できなかった検証を成功したと報告してはいけません。実行可能な構造確認を行い、未実行項目だけ明示します。

### 7. repositoryへ反映する

GitHub書き込みToolが使える場合は、作成または更新したMarkdownをrepositoryへCommitします。

ユーザーがbranchやPRを指定している場合はその指示に従います。指定が無い場合は、利用可能な安全な書き込み経路で変更を反映し、作成したファイルとCommit結果を報告します。

## `mechanism-note`との併用

同じテーマで概要ノートと仕組みノートを両方作る場合は、同じカテゴリとコレクションへ配置することを優先します。

概要ノートは「何か、なぜ重要か、主要概念」に集中し、仕組みノートは「どう動くか、内部で何が起きるか」に集中させます。

## Output

完了時は次を簡潔に報告します。

- 作成または更新したノートのタイトル。
- repository内のファイルパス。
- 新規作成か既存更新か。
- 実行した検証。
- Commit結果。

会話の長い再要約は出力せず、完成したノートをrepository側の成果物として扱います。
