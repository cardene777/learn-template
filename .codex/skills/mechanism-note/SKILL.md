# Mechanism Note

現在のチャットで話し合った内容を、後から「内部でどう動くか」を追える仕組みノートへ整理し、対象Learn repositoryへ保存します。

ユーザーに`contents/`の配置、frontmatter、ファイル名、検証方法、Commit方法を指定させないでください。repositoryを読んでSkill側で判断します。

## Sourceの優先順位

ノートのSourceは次の順で扱います。

1. 現在のチャットでユーザーと話し合った内容。
2. ユーザーがチャットへ提示したURL、ファイル、コード、資料。
3. 対象repository内の既存ノートと構成情報。

ユーザーが追加調査を依頼していない場合、会話に無い内部仕様を推測で埋めないでください。

処理順序、責務分担、状態変化などが会話から確定できない場合は、断定せず「未確認事項」として残します。

## Mechanism Noteの責務

仕組みノートでは主に次を整理します。

- 主要コンポーネントと各責務。
- 入力から出力までの処理フロー。
- データ、状態、権限、メッセージなどの受け渡し。
- コンポーネント同士の依存関係。
- 分岐条件や重要な実行順序。
- 失敗しやすい箇所、制約、境界条件。
- 会話で扱ったコードや具体例がある場合の挙動。

テーマの定義、目的、利用場面、主要概念だけを整理する場合は`overview-note`の責務です。

両方のSkillが使われる場合、仕組みノートでは概要説明を最小限にし、内部構造と動作へ集中します。

## 実行フロー

### 1. 対象repositoryを確定する

ユーザーが指定したGitHub repositoryを対象にします。

既に会話内でrepositoryが確定している場合は再質問しません。

### 2. repositoryのノート構成を確認する

最低限次を確認します。

- `contents/`配下のdirectory構成。
- 同じテーマまたは近いテーマの既存Markdown。
- 近隣ノートのfrontmatter。
- ファイル名、`id`、`permalink`、`order`、カテゴリ、コレクションの命名規則。

frontmatterの項目を記憶だけで固定しないでください。現在のrepositoryにある近隣ノートをSource of Truthとして扱います。

### 3. 配置先を決める

既存カテゴリとコレクションで自然に分類できる場合はそこへ追加します。

適切な分類が無い場合だけ、新しいカテゴリまたはコレクションを作ります。その場合も既存のslugと表示名の規則に合わせます。

同一テーマの仕組みノートが既にある場合は、重複ファイルを増やす前に既存ノートの更新を優先します。ただし既存本文を不用意に削除せず、会話内容を自然に統合します。

### 4. 会話内容から仕組みを抽出する

ユーザーがテーマを指定した場合は、そのテーマに関係する会話だけを抽出します。

仕組みを理解するため、会話から最低限次を抽出します。

1. 何が処理を開始するか。
2. どのコンポーネントが関与するか。
3. どの順序で処理されるか。
4. どのデータや状態が変化するか。
5. 最終的に何が出力または確定するか。
6. どこに失敗条件や重要な制約があるか。

会話に存在しない工程を「一般的にはこうだから」という理由だけで追加しません。

### 5. Markdownを書く

近隣ノートのfrontmatter形式を踏襲します。

本文はテーマに応じて調整しますが、基本的には次の情報が追える構成にします。

```markdown
## 仕組みの要約

## 構成要素

## 処理フロー

## データ・状態の変化

## 重要な分岐と制約

## 具体例

## 未確認事項
```

情報が無い見出しを機械的に残さないでください。

処理フローや関係性が複数ステップになる場合はMermaidを積極的に使います。例えばsequence diagram、flowchart、state diagramのうち、テーマを最も正確に表せるものを選びます。

コードは、会話で扱ったコードまたは仕組みの理解に直接必要な最小例だけを載せます。

### 6. 検証する

保存前に次を確認します。

1. frontmatterが近隣ノートのschemaと一致している。
2. `id`と`permalink`が既存ノートと衝突していない。
3. 配置先のカテゴリとコレクションが妥当である。
4. 処理フローに会話上の根拠があり、推測した工程を事実として書いていない。
5. Mermaidを使った場合はnode名、矢印、処理順序が本文と矛盾していない。
6. 同一テーマの既存仕組みノートを不用意に重複作成していない。
7. repositoryの実行環境を使える場合は`npm run check`を実行する。

CLIを実行できない環境では、実行できなかった検証を成功したと報告してはいけません。実行可能な構造確認を行い、未実行項目だけ明示します。

### 7. repositoryへ反映する

GitHub書き込みToolが使える場合は、作成または更新したMarkdownをrepositoryへCommitします。

ユーザーがbranchやPRを指定している場合はその指示に従います。指定が無い場合は、利用可能な安全な書き込み経路で変更を反映し、作成したファイルとCommit結果を報告します。

## `overview-note`との併用

同じテーマで概要ノートと仕組みノートを両方作る場合は、同じカテゴリとコレクションへ配置することを優先します。

概要ノートは「何か、なぜ重要か、主要概念」に集中し、仕組みノートは「どう動くか、内部で何が起きるか」に集中させます。

## Output

完了時は次を簡潔に報告します。

- 作成または更新したノートのタイトル。
- repository内のファイルパス。
- 新規作成か既存更新か。
- 実行した検証。
- Commit結果。

会話の長い再要約は出力せず、完成したノートをrepository側の成果物として扱います。
