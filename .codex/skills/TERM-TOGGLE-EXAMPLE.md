# 用語補足トグルの実例

Source MarkdownにはClassやStyleを書きません。
トグルは「略語を展開して一文だけ書く用語辞典」ではなく、本文の流れを止めずに理解を深める補助Sectionとして使います。

本文では、まずその用語が必要になる場面を短く示します。

例えば、同じRequestを後からそのまま再利用されると、意図しない二重処理につながる場合があります。
このような再利用を検知しやすくするため、Requestへ一度限りの値を含める設計があります。

<details>
<summary>NonceとReplayを具体的に見る</summary>

`Nonce`は、1回のRequestや署名対象へ割り当てる値です。
受信側は、その値が自分の想定したものか、すでに使われていないかを確認します。

**どんな形式か。**

ProtocolごとにField名や長さは異なりますが、Payloadの一部として文字列やByte列を持つ形が一般的です。
例えば概念的には次のような形です。

```json
{
  "nonce": "7f3c9a..."
}
```

このJSONは特定仕様の固定Schemaを示すものではなく、NonceがDataの一部として運ばれる形を説明するための例です。
実際のField名、型、長さ、生成規則は対象仕様の一次情報で確認します。

**Flowではどう使うか。**

1. ServerがNonceを発行します。
2. ClientはそのNonceをRequestや署名対象へ含めます。
3. Serverは受信時に、Nonceが期待した値か、未使用かを確認します。
4. 正常に受理したら、そのNonceを使用済みとして扱います。

**Replayとの関係。**

`Replay`は、過去に一度ValidだったRequestや署名Dataを再送し、同じ処理をもう一度成立させようとすることです。
Nonceを毎回変え、使用済みかどうかを確認すると、過去のRequestをそのまま再利用した時に値の不一致や再使用を検知できます。

**読者がここで理解すべきこと。**

Nonceは「一度限りの実行へRequestを結び付けるための値」です。
実際にReplayを防ぐには、Nonceを含めるだけでなく、受信側が発行・期限・使用済み状態を正しく管理して検証する必要があります。

</details>

複雑なObject、Credential、Schema、Message、Evidenceを説明する場合も同じです。
名前と一文定義だけで終わらせず、必要に応じて次をトグルへ含めます。

- なぜその用語が今のFlowに出てくるか。
- 実際にどんなDataや構造を持つか。
- 誰が作り、誰が使うか。
- 主要Fieldや構成要素が何を表すか。
- 次の処理や判断へどう使われるか。
- Versionや標準化Statusに注意が必要か。
- 短い具体例。

公式に固定された形式が無い場合は、形を推測で作りません。
概念例であることを明示するか、形式がまだ定まっていないこと自体を説明します。

## 表示について

色、枠、余白、開閉IconはBuildされた記事側のCSSで自動的に付きます。
Markdownへ`class`、`style`、`markdown="1"`を追加しません。

## 禁止例

次は不十分です。

```html
<details>
<summary>最初に押さえる基本用語</summary>

- **Credential**: 検証可能な情報です。
- **Binding**: Dataを結び付ける仕組みです。
- **Nonce**: 一度限りの値です。

</details>
```

これでは、どんな形式か、誰が使うか、Flow上で何に必要かが分かりません。
重要語についてこの程度の説明しかない場合は`Shallow Required Toggle`として未完成扱いにします。

また、重要なRequirementをトグルだけへ隠してはいけません。
例えば「未知のConstraintは必ず拒否する」というSecurity上重要なRuleがある場合、そのRuleは本文へ明記し、トグルには`Constraint`という用語自体の補足を置きます。
