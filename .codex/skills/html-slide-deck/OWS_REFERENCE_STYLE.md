# OWS Reference Style

この文書は、OWS参照PDFの見た目をスライド生成の一次基準として固定するためのルールです。
新しいテンプレートやDiagramを作る時は、一般的なスライドデザインではなく、必ず参照PDFの具体的なページ構成から派生させます。

## 最優先ルール

**参照PDFに近い構図が存在するのに、独自の箱図やネットワーク図を発明してはいけません。**

新規パターンは以下の順序で作ります。

1. 参照PDFから最も近いページを1枚以上選びます。
2. そのページの構図を言語化します。
3. 線幅、余白、ラベル位置、枠の使い方、情報密度を写します。
4. 内容だけをプレースホルダーへ置き換えます。
5. 既存の承認済みテンプレートと横並びで確認します。
6. 参照PDFと並べて違和感がある場合はテンプレート化しません。

「関係図だからHub」「複数要素だからNetwork」のように一般的な図法から逆算してはいけません。

## PageとPDFの役割

Pageの外枠は`pages/`配下の承認済みPage Templateを正とします。
参照PDFはContent Region内部の視覚言語と情報構成の一次参照です。

したがって新しいDiagramやCompositionが、ヘッダー、タイトル、リード、ページ番号を独自に変更してはいけません。

通常スライドでは以下を固定します。

```text
Header        承認済みPage Template
Title         承認済みPage Template
Lead          承認済みPage Template
Content       OWS参照PDFの視覚文法を適用
```

タイトル強調帯はPage Template側で管理します。
強調帯は文字幅にぴったり合わせます。
Diagram側で別のタイトル装飾を追加しません。

## 参照PDFから抽出した視覚文法

### 1. Editorial Grid

参照PDF p10の4特徴ページを基準にします。

- 4列をカードで囲まず、各列上部の細い水平罫線で区切ります。
- 小さな番号と英字ラベルを上に置きます。
- 大きめの日本語見出しを左揃えにします。
- その下に短い説明を置きます。
- 下部に具体例や小さな図を置きます。
- 列全体を濃い枠や塗りで囲みません。
- 情報は上から「ラベル → 見出し → 説明 → 具体例」の順に流します。

この構図は「同格の3〜4要素」「特徴比較」「責務の並列整理」に優先します。

### 2. Structured List + Notes

参照PDF p17のAPI仕様ページを基準にします。

- 左側は表ではなく、細い区切り線を使った構造化リストとして見せます。
- 行の主情報は左揃えです。
- 小さなTOKENなどのタグを行末に置けます。
- 右側は独立した説明Boxを縦に積みます。
- 説明Boxは白または薄い紙色で、線は細くします。
- 重要な1項目だけ赤系の枠で強調できます。
- 右側の説明BoxをカードUI化しません。

この構図は「仕様一覧」「API一覧」「ルール一覧」「左に事実、右に解説」に優先します。

### 3. Before / After Architecture

参照PDF p20の既存資産との関係ページを基準にします。

- 左右に大きな2領域を置きます。
- 各領域は薄い枠で囲みます。
- 領域上部に小さな英字ラベルと日本語説明を置きます。
- システム境界は金系の破線枠で示します。
- 新規追加要素は金系の斜線ハッチで示します。
- 既存要素は白地の細枠で示します。
- 接続線は原則として垂直または水平です。
- BeforeとAfterでNode位置や幅を可能な限り揃えます。

この構図は「変更前後」「追加点」「既存資産への差し込み」「提案前後比較」に優先します。

### 4. Sequence / Time Flow

承認済み`diagrams/sequence/standard/`を基準にします。

- Actorは細い枠です。
- Lifelineは薄い破線です。
- RequestとResponseを別Stepにします。
- Requestは実線、Responseは破線にします。
- 色は意味で使います。
- フェーズ列はStep範囲から算出します。
- 規格列やタグは標準版には置きません。
- 図全体をContent Region内で中央寄せします。

### 5. Boundary / Architecture

参照PDFのArchitectureページとBefore / Afterページを基準にします。

- Zoneは大きな境界として見せます。
- Zone Labelは小さなモノスペースまたは小さな補助見出しにします。
- 境界内のNodeは少数に絞ります。
- 境界自体の意味を主役にする場合、Nodeを増やして情報密度を上げません。
- 新規要素だけ斜線ハッチを使えます。
- すべての領域へ機械的にハッチを入れません。

## OWSらしいNode

Nodeは汎用カードではありません。

- 角丸は使いません。
- 影は使いません。
- 上端の太い色帯は使いません。
- 強い塗りつぶしは使いません。
- 基本は白または紙色の細枠です。
- 重要な意味は枠色、細いハッチ、ラベル色で示します。
- Node内部の文字量が少ない時は中央揃えを使えます。
- 説明量が増える時は左揃えに切り替えます。
- Nodeの外に説明を置ける時は、Boxを大きくして文章を詰め込みません。

## 色

色はPDF内での役割に合わせます。

```text
Black / Gray  本文、既存、構造線
Gold          新規、提案、注目、境界
Red           危険、未承認、外部、拒否
Green         許可、保護、署名、安全側
```

色面よりも線と小さなラベルを優先します。

## 線

- 標準枠線は細くします。
- セクション区切りはさらに細くします。
- 破線は境界やLifelineなど意味がある時だけ使います。
- 矢印は水平直線または垂直直線を最優先します。
- 直交折れ線は1回までを基本にします。
- 斜め線は参照PDFに同種表現がある場合だけ使います。
- 線を増やして関係を表現する前に、配置で関係を表現できないか検討します。

## 余白

OWS参照PDFでは余白がデザインの一部です。

- 要素同士を均等に詰めません。
- 見出しと本文の間には明確な呼吸を残します。
- Diagram全体がContent Regionを埋める必要はありません。
- ただし片側だけ不自然に空く構図は禁止します。
- ページの視覚重心は中央または意図した主役側に置きます。

## 見出し

- 見出しに読点`、`を入れません。
- 見出しは短くします。
- タイトルと小見出しの強調処理は承認済みPage Templateに合わせます。
- 独自の下線や背景帯を追加しません。

## 新規Diagramの選び方

まず以下から最も近い参照構図を選びます。

```text
同格要素             → Editorial Grid
仕様一覧             → Structured List + Notes
変更前後             → Before / After Architecture
時間順               → Sequence / Time Flow
境界と内部構造       → Boundary / Architecture
```

ここに当てはまらない場合でも、いきなりHubやNetworkを作りません。
参照PDF内から視覚的に近いページを探し、その構図から派生させます。

## 禁止

- 参照PDFに根拠のないHub-and-Spokeをデフォルトで作ること。
- 参照PDFに根拠のない放射状Networkをデフォルトで作ること。
- 色付きカードを並べること。
- Box上端へ太い色帯を付けること。
- 丸角、影、グロー、グラデーションを追加すること。
- すべての領域へ同じハッチを付けること。
- すべてのNodeを同じカードコンポーネントで作ること。
- Content Regionの意味に関係なく対称配置を選ぶこと。
- 一般的なダイアグラム記法をOWSの見た目より優先すること。

## Reference Review

新しいTemplateまたはDiagramを完成扱いする前に必ず以下を並べます。

```text
左   参照PDFの近いページ
中   承認済み既存Template
右   新規Template
```

以下を目視確認します。

- 紙面の密度が近い。
- 線の細さが近い。
- Boxの使い方が近い。
- ラベルサイズが近い。
- 色の量が近い。
- 余白の取り方が近い。
- 視覚重心が近い。
- Web UIや一般的なDiagramに見えない。

1つでも大きく外れる場合はFAILです。

## 完成条件

新規パターンは「意味が伝わる」だけでは完成ではありません。
**参照PDFの別ページとして混ぜても違和感が少ないこと**を完成条件にします。
